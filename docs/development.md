# Development

**English** · [中文](development.zh-CN.md) · [README](../README.md)

Use a source checkout, Node.js 22+, and npm. Enter `live-delivery/` from the repository root; all subsequent commands run there.

The runtime targets macOS and Linux. Linux task identities use process start ticks;
macOS uses BSD `ps` status and start time with a fixed locale. Native Windows is
rejected before installation or task-host startup.

`.github/workflows/test.yml` runs the checks on Linux and macOS on GitHub,
using local test fixtures with no model credentials.
Do not infer a macOS pass from a Linux run: record the actual runner and result
for each platform before publishing a tested-platform claim.

```bash
cd live-delivery
npm ci
npm run verify
```

`verify` builds the runtime, checks TypeScript, runs the offline regression suite, and validates release metadata, documentation links, and the runtime file list. It does not call a model or use an API key. `npm run format:check` checks formatting; `npm run format` applies it.

## Source layout

| Path                                               | Contents                                                            |
| -------------------------------------------------- | ------------------------------------------------------------------- |
| `.agents/plugins/marketplace.json`                 | Repository marketplace index pointing to `live-delivery/`           |
| `live-delivery/.codex-plugin/plugin.json`          | Codex plugin manifest                                               |
| `live-delivery/src/delivery/`                      | Tasks, budgets, feedback, and immutable version snapshots           |
| `live-delivery/src/workbench/`                     | HTTP API, previews, access control, and hosted task management      |
| `live-delivery/src/integration/`                   | MCP, hook workflow, and native-to-delivery session binding          |
| `live-delivery/src/harnesses/`                     | Native protocol and process adapters, including Codex and Qwen Code |
| `live-delivery/ui/`                                | Browser interface and locally bundled assets                        |
| `live-delivery/skills/`                            | Delivery via `$ld:go`; installation guidance via `$ld:install`      |
| `live-delivery/src/prompts/tool-descriptions.json` | Source of MCP tool descriptions                                     |
| `live-delivery/test/`                              | Protocol, snapshot, lifecycle, native Codex, and browser checks     |
| `live-delivery/scripts/`                           | Build, release checks, packaging, and dependency notices            |
| `live-delivery/dist/`                              | Self-contained runtime generated by the build                       |
| `docs/`                                            | Public documentation, diagrams, and demo assets                     |

The marketplace index and plugin manifest are installation metadata, not caches. `.github/`, the READMEs, and governance files stay at the repository root. Build and dependency configuration lives in `live-delivery/`.

Within `live-delivery/`, do not edit `src/*.generated.ts` or `dist/` by hand. Commit generated runtime changes with the source so a release can be installed without dependencies. The build regenerates UI assets, copies the root `LICENSE` into the plugin, and embeds dependency license texts as comments in `dist/`. Keep private experiments, model transcripts, product plans, and credentials outside the repository.

The first release uses `QWEN_LD_PROTOCOL = 'v1'` and `stateVersion: 1`. State readers accept this format only; prototype-format conversion is not part of the plugin. Artifact versions increment independently of the protocol version.

User guides in `docs/` have English and `.zh-CN.md` versions. Governance documents are kept in English. Update both when changing configuration, commands, or behavior, and retain the language links at the top. Keep JSON field names and executable commands consistent across languages.

To add a CLI-only harness, implement `CliAdapter` in `src/harnesses/<name>/`, then register its entry and installation configuration. A CLI-only integration does not implement `HostedExecution`. Add it only for browser-owned execution; interrupt-and-resume feedback is optional, not a delivery requirement.

Delivery receives a workspace and an already-bound session key and does not read native configuration or events. Delivery task IDs own snapshots, session keys scope feedback, and instance IDs scope runtime bindings. The `dist/` entry points and `.live-delivery` delivery record format stay unchanged.

## Build a package and try it

```bash
npm run package -- --out ./release
mkdir -p ./release/unpacked
tar -xzf ./release/qwen-live-delivery-codex-0.1.0.tgz -C ./release/unpacked
./release/unpacked/package/live-delivery/install.sh --install-only --workspace /path/to/project
```

Start a new Codex session **in a separate project directory**. Use `install.sh`: it stages only runtime files even when invoked from a source checkout. Registering the development root directly with `codex plugin marketplace add` may copy dependencies and test outputs; avoid that path.

Keep `package.json`, `package-lock.json`, and `tsconfig.json` in `live-delivery/`: they define
the Node.js project, reproducible dependencies, and TypeScript configuration.
`src/prompts/` is build input; generated `dist/` files are the installed runtime.
The repository tracks `dist/` so a checkout can be installed without a development build.

The npm package is intentionally `private: true`. The packaging script combines the allowlisted plugin files with root documentation and the marketplace index, preserving the `live-delivery/` layout. It excludes source, tests, and dependencies. This project does not publish to the npm registry.

## Native Codex compatibility

Install the CLI version you want to validate, then run:

```bash
node test/setup-native.mjs
node test/provider-env-native.mjs
node test/workbench-native.mjs
QWEN_LD_TEST_FEEDBACK=1 node test/workbench-native.mjs
npm run test:codex
```

Set `CODEX_BIN` to choose a CLI executable. Set `QWEN_LD_TEST_PACKAGE` to the unpacked `package/live-delivery/` directory to test that package rather than the development runtime. Tests do not modify your normal Codex settings or installed plugins. Live model evaluation is a separate, opt-in manual exercise; it consumes the operator's own quota.

## Qwen Code CLI compatibility

After `npm ci`, run these commands from `live-delivery/`:

```bash
npm run build
npm install --no-save --package-lock=false playwright@1.61.1
npx playwright install chromium
npm run test:qwen
```

The test uses two real `qwen` processes in the same temporary workspace and Chromium. A local fixture supplies model responses, so no API key is required and your Qwen settings are not changed. It checks CLI start, V1/V2 browser previews, feedback, wrap-up, and session isolation. Set `QWEN_BIN` or `CHROMIUM_PATH` to use a specific executable.

## Browser checks

Python 3 and Playwright are optional development dependencies:

```bash
python3 -m venv .venv
.venv/bin/pip install -r test/requirements.txt
.venv/bin/python -m playwright install chromium
.venv/bin/python test/simple-browser.py artifacts/workbench
```

`CHROMIUM_PATH` can select an existing Chromium executable. Tests use temporary local workspaces and deterministic child fixtures, not your running tasks. Screenshots and reports go to the given output directories, which are excluded from the runtime package. These tests cover controls, artifact isolation, workspace switching, continuation, read-only version cards and pending goals, time-unit conversion, keyboard/IME behavior, execution states, stop-button visibility at mobile and desktop widths, contextual tour placement, and persistent opt-out.

A manual smoke test should also check a real task end to end: start directly, change the next version through chat, inspect two distinct versions, send feedback, download a ZIP, and request wrap-up. Report both the Codex version and the model/provider used; do not infer live-model quality from the deterministic fixture.

## Release

Release the skill, hooks, MCP server, and workbench as one tested package.

1. Keep the version consistent in `package.json`, `package-lock.json`, `.codex-plugin/plugin.json`, `qwen-extension.json`, `src/delivery/core.ts`, `src/integration/server.ts`, and `src/harnesses/codex/native-rpc.ts`. Update archive examples in both languages.
2. From a clean checkout, run `npm ci`, `npm run verify`, `npm run format:check`, and `npm audit`, then the [native Codex checks](#native-codex-compatibility). Require passing Linux and macOS checks; UI changes also need the [browser checks](#browser-checks). Record the tested Node.js and Codex versions.
3. [Build and unpack the archive](#build-a-package-and-try-it), then test the unpacked package:

   ```bash
   QWEN_LD_TEST_PACKAGE="$PWD/release/unpacked/package/live-delivery" node test/setup-native.mjs
   QWEN_LD_TEST_PACKAGE="$PWD/release/unpacked/package/live-delivery" node test/provider-env-native.mjs
   QWEN_LD_TEST_PACKAGE="$PWD/release/unpacked/package/live-delivery" npm run test:codex
   QWEN_LD_TEST_PACKAGE="$PWD/release/unpacked/package/live-delivery" QWEN_LD_TEST_FEEDBACK=1 npm run test:codex
   ```

   Use a fresh output directory for each candidate; packaging will not overwrite an existing archive. Inspect the archive and screenshots for credentials, private links, workspaces, logs, and assets without redistribution rights. Automated checks do not replace this review.

Tag the tested commit, for example `qwen-live-delivery-codex-v0.1.0`, and attach the archive and `SHA256SUMS` to the GitHub Release. State the supported platforms, tested Codex versions, and known limitations. Keep published tags and archives unchanged; fixes receive a new version.

The first release does not need a changelog. For later releases, describe user-visible changes and any migration steps. Confirm that the private reporting channel in [SECURITY.md](../SECURITY.md) is available before publishing.
